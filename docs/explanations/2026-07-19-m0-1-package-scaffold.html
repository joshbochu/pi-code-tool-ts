Background

Before this pull request, pi-code-tool-ts was a design repository: goals, roadmaps, and a meticulous milestone plan, but no package a machine could install or a real Pi process could load. PR #2 is the moment the project becomes executable without becoming a product. To see why that distinction is so carefully drawn, it helps to start farther out than the diff.

Deep background for beginners (safe to skip if you already know Pi packages)

What Pi is, in one paragraph

Pi is a coding-agent CLI. Like many agent tools, it can be extended: third-party packages register tools, slash commands, event hooks, and other behavior. An extension is not a separate daemon by default. When Pi starts, it discovers packages, loads their TypeScript entrypoints, and calls a factory function inside the Pi process itself.

What a Pi package looks like

A Pi package is ordinary npm metadata plus one extra field. In package.json you declare: 

{
  "name": "my-extension",
  "keywords": ["pi-package"],
  "pi": {
    "extensions": ["./src/extension.ts"]
  }
}

Pi reads pi.extensions, loads each module (TypeScript is accepted directly; there is no mandatory compile step), and invokes the module’s default export. That default export is a factory: a function that receives an ExtensionAPI object. Through that API, the factory can register tools, commands, and so on.

Definition · Extension factory

A function Pi calls at startup with an ExtensionAPI. Anything the factory registers becomes part of that Pi session. Anything it does not register simply does not exist.

Why Bun and TypeScript show up here

This repository is intentionally a Bun-managed TypeScript package. Bun provides the package manager, test runner, and a convenient way to spawn processes. TypeScript is checked with tsc --noEmit (type-check only; no emitted JavaScript), because Pi loads the .ts sources itself. That combination is the project’s development path for everything that follows.

The larger product ambition (not in this PR)

Eventually, pi-code-tool-ts aims to give Pi a TypeScript “code mode”: a durable way for the model to run TypeScript against tools without shipping every intermediate result back through the prompt. That future involves subprocesses, IPC, trust contracts, and a model-facing code tool. None of that is present in PR #2. M0.1 only proves that the package can be loaded.

Key constraint · Inert on purpose

M0.1 forbids product behavior. The extension factory must register no tools, commands, events, timers, workers, sockets, or subprocesses. A smoke harness may launch Pi as test infrastructure, but the extension itself must remain a no-op.

What “proof” means in this unit

The plan distinguishes two layers of evidence:

  • Fast checks — bun run check type-checks and runs unit tests. These never start Pi.
  • Smoke load — bun run smoke:pi launches the project-pinned Pi CLI against this package root, speaks a tiny RPC conversation, and also proves that a missing extension path fails.

That second layer exists because unit tests alone cannot prove the real loader path. A green test suite could still leave you with a package.json Pi never reads.

Intuition

The essence of PR #2 is a handshake with an empty hand. Pi must be able to find the package, load the factory, call it, and continue. The factory must accept the call and do nothing. Everything else in the PR exists to make that claim checkable.

A toy story with concrete data

Imagine Pi as a concierge who, at opening time, walks a list of vendor booths. For each booth, the concierge reads a sign on the door (pi.extensions), opens the door (loads the module), and says: “Here is the building API—hang your tools if you like.”

Most future booths will hang wrenches and registers. The M0.1 booth hangs nothing. It still must open. If the door is locked, or the concierge never visits, later work is fantasy.

Why a hostile Proxy appears in the unit tests

Saying “we do not use the API” is easy in a code review and easy to break later with a casual pi.registerTool(...). The unit test passes a Proxy that throws on any property access. If the factory so much as reads a field, the test explodes.

This is not a mock of Pi’s real API surface. It is a mousetrap: any accidental contact snaps shut.

Why the smoke test needs a positive and a negative path

Consider a broken smoke script that launches Pi with flags so gentle that Pi exits zero without ever loading your package. Green output, empty proof. PR #2 guards against that in two ways:

  1. Positive path — load the package root (-e .), send an RPC request {"id":"m0.1-smoke","type":"get_state"}, and require a matching successful response line on stdout.
  2. Negative path — point Pi at a deliberately missing file ./src/__m0_1_missing_extension__.ts and require a non-zero exit. If even garbage paths “succeed,” the harness is lying.

Isolation in one picture

The smoke environment is intentionally stingy. It sets PI_CODING_AGENT_DIR to a fresh temp directory, PI_OFFLINE=1, and PI_TELEMETRY=0, then copies only a short allowlist of host variables (PATH, HOME, locale, and a few Windows process basics). The user’s models, credentials, and extension soup stay out of the proof.

Intuition pump

Think of M0.1 as testing the electrical outlet in an empty room before you buy furniture. You plug in a lamp tester (the smoke harness), confirm power (Pi loads the package), confirm the tester is not broken (negative control), then unplug everything and leave the room bare (inert factory).

2. Strict TypeScript without emit

tsconfig.json turns the typechecker into a gate, not a compiler. noEmit: true keeps the tree free of generated JavaScript. The include list covers product code, tests, and—after the polish commit—the smoke script: 

{
  "compilerOptions": {
    "strict": true,
    "noEmit": true,
    "moduleResolution": "bundler",
    "verbatimModuleSyntax": true,
    "noUncheckedIndexedAccess": true,
    "types": ["bun-types"]
  },
  "include": ["src/**/*.ts", "test/**/*.ts", "scripts/**/*.ts"]
}
Why scripts joined include

Without scripts/**/*.ts, bun run typecheck could stay green while smoke-pi.ts drifted into type errors. The smoke harness is not product runtime, but it is mandatory evidence. Typechecking it closes a blind spot.

3. The inert factory

The entire product surface of M0.1 fits in a handful of lines: 

import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

/**
 * M0.1 inert Pi extension factory.
 * Proves the package can load. Registers nothing and starts nothing.
 */
export default function piCodeToolTsExtension(_pi: ExtensionAPI): undefined {
  return undefined;
}
  • import type keeps the Pi import eraseable—no runtime require of Pi from the factory module’s value space beyond types.
  • The parameter is named _pi to signal intentional non-use.
  • The return type is literally undefined, matching “no extension instance object.”

4. Unit tests as behavioral fences

test("default export is a function", () => {
  expect(typeof extension).toBe("function");
});

test("returns undefined without throwing", () => {
  expect(extension({} as never)).toBeUndefined();
});

test("does not touch the Pi API (hostile Proxy)", () => {
  const hostile = new Proxy({}, {
    get() { throw new Error("API property access is forbidden in M0.1"); },
  });
  expect(extension(hostile as never)).toBeUndefined();
});

Three claims, three fences: export shape, pure call, zero API contact. Together they encode the inertness rule in a form CI can fail loudly.

5. The smoke harness, in layers

scripts/smoke-pi.ts is the longest file in the PR, but it has a calm structure. Read it top-down as four layers.

1
Constants and types Shared RPC vocabulary lives once: SMOKE_RPC_ID = "m0.1-smoke", SMOKE_RPC_COMMAND = "get_state", SMOKE_RPC_RESPONSE_TYPE = "response", and the missing path ./src/__m0_1_missing_extension__.ts. A small SmokeRpcRequest object is JSON-stringified later so the request and the matcher cannot drift apart.
2
Isolated environment createSmokeEnvironment(agentDir) builds a minimal env for the child. Fresh PI_CODING_AGENT_DIR, offline and telemetry flags, then a careful allowlist from the parent process.
3
Process spawn helper runPi(extensionSource, agentDir, rpcInput) always uses the project-local binary under node_modules/.bin, with --offline --no-extensions -e <source> --mode rpc --no-session. Stdin carries the optional RPC line; stdout/stderr are captured in full.
4
Main sequence Resolve version → positive package-root load with RPC match → negative missing-path load must fail → print one success line → always delete the temp agent dir in finally.

What this PR intentionally does not contain

  • No model-facing code tool.
  • No Bun subprocess runtime, Worker, or IPC channel in product code.
  • No TypeScript evaluation of model-written programs.
  • No trust/opt-in contract (that is M0.2).
  • No proof of pi install from a registry—only explicit package-root loading via -e ..
