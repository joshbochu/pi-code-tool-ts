# M0.1 — Package scaffold

## Problem

Before this unit, the repository was design-only: product goals and milestone plans existed, but nothing could be installed, type-checked, unit-tested, or loaded by the real Pi CLI. There was no proof that a Bun-managed TypeScript package could satisfy Pi's extension contract.

## Mental model

A Pi package is ordinary npm metadata plus a small `pi` manifest. Pi discovers extension entrypoints from `package.json` → `pi.extensions`, loads each TypeScript module (via jiti; no compile step), and calls the default-export factory with an `ExtensionAPI` object.

M0.1 stops at that handshake. The factory is deliberately inert: it accepts the API, returns `undefined`, and registers no tools, commands, events, or processes. The unit proves the development and loading path only.

## Code tour

1. `package.json` — package identity, ESM mode, `private: true`, scripts, `pi.extensions`, peer/dev dependency on `@earendil-works/pi-coding-agent`.
2. `tsconfig.json` — strict TypeScript with `noEmit: true` so Pi loads sources directly.
3. `src/extension.ts` — type-only import of `ExtensionAPI`; default-export factory `piCodeToolTsExtension` that returns `undefined` without reading the API.
4. `test/extension.test.ts` — export-shape checks plus a hostile `Proxy` that throws on any property access, proving the skeleton never touches Pi.
5. `scripts/smoke-pi.ts` — isolated RPC startup probe using the project-pinned Pi CLI, plus a missing-extension negative control.
6. `bun.lock` — locked Bun install of development tooling only.

## Protocol or data flow

```text
Project-pinned Pi 0.80.10
  → uses an isolated temporary PI_CODING_AGENT_DIR
  → reads package.json pi.extensions
  → loads src/extension.ts
  → calls default factory with ExtensionAPI
  → factory returns without registering behavior
  → answers an RPC get_state request
```

Smoke path used in this unit:

```text
bun run smoke:pi
  → loads the package root with -e . in offline, no-session RPC mode
  → requires a successful get_state response
  → runs a missing-extension path as a negative control
  → requires that invalid startup to exit non-zero
```

## Try it

```sh
bun install --frozen-lockfile
bun run check
bun run smoke:pi
```

Expected: type-check and three unit tests pass; the pinned Pi CLI reports that the package answered RPC and the missing-extension control failed as expected.

## Tests

**Proven**

- Default export is a function.
- Invoking the factory returns `undefined` and does not throw.
- Invoking with a Proxy that throws on every get still succeeds (no API property access).
- Strict `tsc --noEmit` succeeds and emits no build artifacts.
- Project-pinned Pi 0.80.10 resolves the package root, calls the extension during offline RPC startup with an isolated config, and answers `get_state`.
- The same probe rejects a missing extension path, preventing an early-exit false positive.

**Unproven / intentionally absent**

- No product/runtime child process, Worker, IPC channel, timer, socket, or file watcher. The smoke harness launches Pi and speaks RPC only as test infrastructure.
- No TypeScript evaluation or transformation.
- No model-facing `code` tool, tool adapters, approvals, streaming, or persistence.
- No trusted-execution opt-in contract (M0.2).
- No V0 acceptance fixtures (M0.3).
- Package installation through `pi install` is not covered; the smoke uses explicit package-root `-e .` loading.

## Tradeoffs

- **Inert factory over a “hello” registration.** A toast or no-op tool would feel more demo-like but would mix product behavior into the bootstrap commit and blur the stop gate.
- **Pi types as peer + pinned devDependency only.** The peer stays broad for package compatibility, while the exact development version makes loader and type checks reproducible; runtime dependencies stay empty.
- **`smoke:pi` separate from `check`.** Unit tests do not start Pi. The smoke uses the project-pinned CLI and an isolated temporary config rather than depending on a global Pi installation or user credentials.
- **`@types/bun` as a devDependency.** Needed so `bun:test` type-checks under `tsc`; it is not a product runtime dependency.
- **No empty future source tree.** Files appear only when their idea becomes real, keeping the first commit independently revertible and reviewable.

## Review questions

1. How does Pi discover this package’s extension entrypoint, and which command proves the factory is actually invoked by the real CLI?
2. Why is it correct that this factory runs inside the Pi process, and why does that **not** create a trust boundary for future model-generated code?
3. What is the first file that will later register product behavior (for example the `code` tool), and what must still be absent after this unit?
