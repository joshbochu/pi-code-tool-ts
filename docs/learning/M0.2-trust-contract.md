# M0.2 — Trusted-execution contract

## Problem

M0.1 proved that Pi could load the package, but the package expressed no executable contract for the project's central risk: the planned Bun runtime will run model-written code with the current user's ambient authority. Without a deliberate opt-in and a visible warning, a future runtime could make trusted code execution look safer or more automatic than it is.

## Mental model

The extension now registers one boolean Pi flag, `--allow-trusted-code`, whose default is `false`. Pi parses the command-line value and makes it available through `ExtensionAPI.getFlag()` after extension flags have been registered. When a session starts, the extension checks that value.

Only the exact boolean value `true` counts as consent. Missing values, `false`, and string values remain disabled and silent. Exact opt-in emits a warning that the future TypeScript runtime will have shell-equivalent authority and that a subprocess is not a security sandbox.

The flag is a product consent gate, not a sandbox. M0.2 still registers no `code` tool and starts no runtime, so opting in cannot execute generated code yet. A later execution unit must consult this same contract before exposing trusted execution.

## Code tour

1. `src/extension.ts` defines the stable flag name, CLI description, warning text, and `session_start` check.
2. `test/extension.test.ts` uses narrow hostile Proxies to permit only `registerFlag`, `on`, `getFlag`, and the enabled path's `ui.notify` call.
3. `scripts/smoke-pi.ts` starts the project-pinned Pi CLI without and with the opt-in, then inspects real RPC output for the two paths.
4. `README.md` explains the flag and the fact that no execution behavior exists yet.
5. `PROJECT_PROGRESS.md` records the unit's review state and verification evidence.

## Protocol or data flow

```text
Pi loads src/extension.ts
  → extension registers --allow-trusted-code (boolean, default false)
  → extension subscribes to session_start
  → Pi starts a session
      ├─ flag is not exactly true
      │    → remain silent
      │    → expose no code tool or runtime
      └─ flag is exactly true
           → notify at warning severity
           → still expose no code tool or runtime
```

The warning names the future runtime's ability to read and modify files, read environment variables and credentials, use the network, and spawn commands and child processes. There is no child process, IPC connection, evaluator, notebook state, transcript state, or replay in this flow. The only state is Pi's parsed flag value for the current process.

## Try it

Run the complete automated evidence:

```sh
bun install --frozen-lockfile
bun run check
bun run smoke:pi
```

Expected: seven unit tests pass. The smoke probe reports that project-pinned Pi kept the default path silent, emitted the warning after explicit trusted opt-in, and rejected the missing-extension negative control.

For a human demonstration, start Pi with the package and flag:

```sh
./node_modules/.bin/pi --offline --no-extensions -e . --allow-trusted-code
```

Expected: Pi displays the trusted-code warning when the session starts. It does not add a `code` tool or execute TypeScript. Omitting `--allow-trusted-code` keeps the session silent.

## Tests

**Unit-test evidence**

- The extension remains a synchronous default-exported factory and returns `undefined`.
- It registers exactly one boolean `allow-trusted-code` flag defaulting to `false`.
- The description states that future execution has the same practical authority as an unrestricted shell.
- `false`, `undefined`, `"true"`, and `"false"` all remain silent.
- Exact boolean `true` emits the exact warning at warning severity.
- The warning names shell authority, ambient filesystem/environment/network/process powers, the lack of a security sandbox, and the absence of current execution.
- Hostile Proxies fail on any Pi API or session-context access outside the narrow consent contract.

**Real-Pi smoke evidence**

- Project-pinned Pi 0.80.10 loads the package and answers RPC in an isolated, offline, no-session environment.
- The default launch emits no trusted-execution warning.
- The opted-in launch emits the exact warning and still answers RPC.
- The original missing-extension negative control still exits non-zero.

**Intentionally unproven and absent**

- No model-facing `code` tool exists, even after opt-in.
- No generated TypeScript is accepted, transformed, or executed.
- No product subprocess, Worker, IPC transport, timeout, cancellation, or cleanup mechanism exists.
- The flag does not isolate ambient authority; it records informed consent only.
- Configuration files and environment-variable aliases are unsupported.
- M0.3 acceptance fixtures remain unimplemented.

## Tradeoffs

- **Pi boolean flag over an environment variable.** The opt-in is visible in `--help`, typed by Pi, defaults safely, and is explicit at process startup.
- **Warning at each opted-in session start.** A new session cannot silently inherit dangerous-looking behavior without presenting the consent message again.
- **No placeholder code tool.** Registering even a refusing tool would preview the M4 interface and blur M0's boundary. Absence is the strongest current disabled state.
- **Exact `true` check.** Pi's API can return booleans, strings, or `undefined`; requiring boolean `true` prevents accidental opt-in through a string or missing value.
- **Unit and smoke evidence.** The Proxy tests precisely prove allowed API access, while the separate Pi subprocess proves actual CLI parsing and RPC notification behavior.
- **No copied third-party source.** This unit uses only Pi's public extension API and requires no attribution entry or runtime dependency.
