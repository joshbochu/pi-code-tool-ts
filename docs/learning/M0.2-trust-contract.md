# M0.2 — Trusted-execution contract

## Problem

M0.1 proved that Pi could load the package, but it expressed no executable
contract for the project's central risk: the planned Bun runtime will run
model-written code with the current user's ambient authority. Without a
deliberate opt-in and visible warning, a future runtime could make trusted code
execution look safer or more automatic than it is.

## Mental model

The extension now registers one boolean Pi flag, `--allow-trusted-code`, whose
default is `false`. A session started without the flag stays silent. A session
started with the flag emits a warning that model-written TypeScript will have
shell-equivalent authority and that a subprocess is not a security sandbox.

The flag is a product gate, not a sandbox. M0.2 still registers no `code` tool
and starts no runtime, so opting in cannot execute generated code yet. Later
milestones must consult this same explicit contract before exposing execution.

## Code tour

1. `src/extension.ts` defines the stable flag name, user-facing description,
   warning text, and the `session_start` check.
2. `test/extension.test.ts` uses a narrow Proxy harness to prove the flag shape,
   disabled behavior, enabled warning, and absence of any other Pi API access.
3. `scripts/smoke-pi.ts` starts real project-pinned Pi processes both without
   and with the opt-in, then inspects RPC output for the warning contract.
4. `README.md` states how the current opt-in behaves and what remains absent.
5. `PROJECT_PROGRESS.md` records M0.1 acceptance and M0.2 review evidence.

## Protocol or data flow

```text
Pi loads src/extension.ts
  → extension registers --allow-trusted-code (boolean, default false)
  → extension subscribes to session_start
  → Pi starts a session
      ├─ flag is not true → return silently; execution remains unavailable
      └─ flag is true     → emit shell-authority warning; execution still unavailable
```

There is no child process, IPC connection, code evaluator, model-facing tool,
or durable state in this flow. The only state is Pi's parsed boolean flag value
for the current process.

## Try it

```sh
bun install --frozen-lockfile
bun run check
bun run smoke:pi
```

Expected: four tests pass. The smoke probe reports that project-pinned Pi kept
the default path silent, emitted the warning after explicit trusted opt-in, and
rejected the missing-extension negative control.

For an interactive demonstration, start Pi with the package and flag:

```sh
./node_modules/.bin/pi --offline --no-extensions -e . --allow-trusted-code
```

Expected: Pi displays the trusted-code warning when the session starts. It does
not add a `code` tool or execute TypeScript.

## Tests

**Proven**

- The extension registers `--allow-trusted-code` as a boolean defaulting to
  `false`.
- The flag description states that the authority matches an unrestricted shell.
- The disabled path emits no warning and accesses no Pi API capable of exposing
  a tool or starting work.
- The enabled path emits a warning naming shell-equivalent authority, ambient
  filesystem/environment/network/process powers, and the lack of sandboxing.
- Project-pinned Pi 0.80.10 exhibits the same disabled and enabled behavior over
  an isolated, offline RPC smoke test.

**Unproven / intentionally absent**

- No `code` tool exists, even after opt-in.
- No generated TypeScript is accepted, transformed, or executed.
- No subprocess, Worker, IPC transport, timeout, cancellation, or cleanup logic
  exists.
- The flag does not isolate ambient authority; it records informed consent only.
- Configuration files and environment-variable aliases are not supported.
- M0.3 acceptance fixtures are not implemented.

## Tradeoffs

- **Pi boolean flag over an environment variable.** The opt-in is visible in
  `--help`, typed by Pi, defaults safely, and is explicit at process startup.
- **Warn on each opted-in session start.** Session replacement cannot silently
  carry the dangerous mode into a new session without another visible warning.
- **No placeholder code tool.** Registering a refusing tool would preview the
  M4 interface and blur M0's boundary. Absence is the strongest disabled state.
- **Exact `true` check.** Only Pi's parsed boolean `true` enables the warning;
  strings or missing values do not accidentally opt in.
- **No copied third-party source.** This unit uses only Pi's public extension
  API and requires no attribution entry.
